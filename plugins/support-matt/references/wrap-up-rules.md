# 收尾規範

`implement-stepwise` 使用。

## 收尾

一張 ticket 的全部 commit 完成後執行。**收尾是交接清單，不是稽核報告。**

收尾分三段：

1. **驗證** —— 跑受影響範圍的測試、跨層重複檢查、逐條判定驗收條件。一路做完不停，判定結果**只留在對話**。
2. **定稿前停點** —— 攤出驗證結果，命中條件時附上冷眼審查的建議，等使用者決定。這是收尾唯一的停頓。
3. **定稿** —— 把核對結果寫回 ticket、回報，結束。

**ticket 只在定稿時寫一次。** 驗證結果不先寫回有兩個理由：冷眼審查讀到的 ticket 只有驗收條件原文，不會被同一個 session 的自評（一排 `[x]` 與「達成」依據）帶著走；停點之後的任何修正都發生在寫回之前，寫進 ticket 的永遠是最終狀態。

### 驗證

1. **跑受影響範圍的測試** —— 本次變更所屬的測試專案／模組，不是完整測試套件。完整套件由 `to-acceptance-map` 在整條 branch 結束時跑一次，那裡才是它的位置；每張票都跑一次完整套件，在大型專案會耗掉大量時間而重複驗證同一批東西。

   **涉及多個測試專案時逐一執行，不要用 solution／workspace 層級的單一指令一次跑完。** 跨測試專案並行常因共用資料庫、連接埠、靜態狀態或測試替身而互相干擾，產生單獨跑全綠、一起跑就紅的假失敗，導致你去追一個不存在的問題。
2. **跨層重複檢查** —— 見下方。有刪或併時，該變更走 commit 關卡提交後再往下。
3. **逐條判定 ticket 的 `Acceptance criteria`** —— 見下方判定規則。**判定結果只留在對話，不寫 ticket。**

測試失敗、或有驗收條件部分達成或未達成時，**照樣把其餘步驟做完**，全部攤在停點上，見「發現問題時不要就地修」。

### 跨層重複檢查

commit 前的 consolidation 有個看不到的死角：**同一個行為的單元測試與整合／UI 測試通常寫在不同的 commit 裡**（先寫 service 與它的單元測試，過幾個 commit 才寫端點與它的整合測試）。站在任何一個 commit 上，另一層都還不存在或已經是「既有測試」，所以跨層重複永遠不會被當場發現。

**收尾是這張票唯一兩層都寫完的時點**，所以在這裡做一次，範圍限定**本票新增的昂貴層測試**（整合、UI／E2E，以及日後任何需要真實環境的測試型別）：

逐支問一句——**便宜的那一層是不是已經在驗同一件事？**

- **是，而且昂貴層那支沒有多保護什麼** → 刪掉昂貴層那支。
- **是，但昂貴層另外驗到了真實資料庫、HTTP 管線或瀏覽器 wiring** → 兩支都留，並在回報中說出昂貴層那支多保護了什麼。
- **否** → 留著。
- 同一種昂貴層檢查出現 3 個 case 以上（例如每個端點各一次 401／403，含既有參數化測試的列數）→ **併成一支參數化**，並依 `testing-rules.md` 的「同構家族」逐 case 問它保護的是不是別的 case 保護不到的東西。

規則：

- **只看本票新增的昂貴層測試**，不掃既有的、也不動單元測試——單元測試多幾支不是問題，這一步不是來砍它們的。
- 刪或併之後**重跑該測試專案**，不是只跑剩下的那幾支。
- **刪或併的變更走 commit 關卡提交**，前綴用 `test:`。這是本 skill 唯一允許的純測試收斂 commit——跨層重複要等兩層都寫完才看得到，沒辦法併回當初的 implementation commit。
- **結果要寫進停點的回報**：本票在昂貴層留下幾支、各自保護什麼便宜層測不到的東西；刪了哪幾支、原因是什麼。**一支都沒刪時也要講出留下的那些各保護什麼**——這一步的價值在於逼出那句話，不在於刪掉東西。
- 判不準就留，並在回報中點名，讓使用者決定。

### 驗收條件的判定規則

判定的是**實作有沒有做到**，不是**有沒有測試**。

| 判定 | 條件 |
| --- | --- |
| 達成 | 該行為已實作，並指出它落在哪裡（程式碼位置或測試皆可） |
| 經裁示調整 | 使用者對這一條做過裁示（改做法、縮範圍、不做），實作已照裁示完成；依據寫出裁示內容 |
| 移交 NN | 依相依順序本票做不到，由後續 ticket NN 交付；依據寫出 NN 由哪一條驗收條件或哪段 What to build 承接 |
| 部分達成 | 只做到一部分，明確說出缺哪一塊 |
| 未達成 | 沒做 |

- **「經裁示調整」只用在使用者真的裁示過的條目。** 自己判斷「這條不必做」不算裁示，一律判部分達成或未達成，交給使用者決定。使用者在停點對部分達成或未達成的條目回「就這樣」，定稿時改判經裁示調整。
- **「移交」要先讀到後續 ticket 確實承接。** 找不到承接的票，判部分達成。
- **不得因為「這條沒有對應測試」就判為未達成。** 測試覆蓋是 `to-acceptance-map` 的職責，且該處已有「不適用測試」分類承接本來就不預期有測試的項目。在收尾混用兩把尺，會產生大量假的未達成。
- 指出證據時，**程式碼位置與測試同等有效**。行為若明顯落在某個方法或畫面，指那裡即可。

### 定稿前停點

驗證做完，**停下來回報並等待使用者回應**。這是使用者在這張票上最後一次插手的機會，回報要讓使用者帶著證據決定，不是空手預告。回報固定包含下列各段（冷眼審查一段只在命中條件時出現）：

````md
### 驗證結果待確認

**測試**
`XxxTests`、`XxxIntegrationTests` 逐一跑完，全綠。

**跨層重複檢查**
本票昂貴層留下 2 支：`Detail_權限不足時隱藏編輯` 守頁面依旗標渲染、`Save_併發衝突回 409` 守真實 DB 的並行控制；
刪除 `Detail_草稿狀態顯示文字`（規則已由 `TestXxx.各狀態的顯示文字` 守著），已提交 `test: 移除與單元測試重複的詳細頁狀態文字測試`。

**驗收條件判定**
| # | 判定 | 依據 |
| --- | --- | --- |
| 1 | 達成 | … |
| 4 | 部分達成 | 下拉已實作，缺「退貨單」選項 |

**冷眼審查**
建議跑 `/code-review a1b2c3d .ai/issues/0042-xxx/03-yyy.md`：命中 A（本票實作 BR-03 的實作約束）、C（新增刪除端點）。

回「繼續」我會把核對結果寫回 ticket 並結束；回「審查」我會執行上面的審查。
要補做或修正什麼，現在講。
````

使用者的回應處理：

- **回「繼續」** → 進定稿。
- **提出補做或修正** → 走 commit 關卡提交，之後**回到驗證整段重跑**（不是只跑改到的部分），再停一次。
- **回「審查」**，或沒命中條件但使用者主動要求 → 依下方「冷眼審查」執行。
- **使用者自行執行審查後把結果貼回** → 與自己執行的審查結果同樣處理。
- **回應不明確** → 當作尚未確認，問清楚要做什麼。

**停點的「繼續」只代表進定稿**，與 commit 關卡的「繼續」一樣，都不構成執行審查的授權。

### 冷眼審查

收尾回答「交付了什麼」，冷眼審查回答「交得對不對」。這是兩件事，收尾不替代它——但不是每張票都值得付這筆成本：使用者已逐 commit 過目，branch 層另有原生 review，而 Matt 的 `/code-review`（兩個冷啟動 sub-agent 讀 diff）實測 174,646 token。逐票跑它，換得到的只有原生 review 給不了的兩樣：**Spec axis 拿規格對照實作**，以及**高風險改動在上下文還在時就被冷眼看過**。所以只在命中下列任一條時於停點建議：

| 條件 | 判斷依據 |
| --- | --- |
| **A. 有硬約束可對照** | ticket 引用了規格文件的實作約束、關鍵決策或 `VC-xx`。以 ticket 寫到的為準，**不為了判斷去讀規格文件** |
| **B. 實作偏離計畫** | 驗證判定有「經裁示調整」或「部分達成」，或使用者在 commit 關卡改過實作方向 |
| **C. 高風險區域** | 本票 diff **實際**動到權限、交易邊界、併發、schema／資料遷移、不可逆操作（刪除、覆寫外部狀態）。看 diff 動到哪裡，不看票的主題 |

建議的規則：

- **指令寫成可直接複製執行的一整行**，並寫出命中哪幾條與具體依據。
- **fixed point 用本票第一個 commit 的 parent SHA**，審查範圍才會只限本票；沒給的話 `/code-review` 會反問，隨手回 `main` 就變成審整條 branch。
- **規格來源直接帶本票 ticket 的路徑。** 不帶的話 `/code-review` 會自己找規格，在 local markdown tracker 下很容易抓到整份 `spec.md` 或 `issue-doc.md`，把別張票的需求報成缺漏。
- **一條都沒命中就整段不提**，不要寫「本票不需審查」。
- 判斷只看上面的事實成不成立，**不評實作對錯**——那正是要交給冷眼的部分。

執行與結果處理：

- **只在使用者回「審查」或主動要求時執行**，照建議的指令調用 `/code-review`。審查由它自己的 sub-agent 進行，本 session 只接收彙整後的報告。
- **報告依 `/code-review` 的兩軸格式原樣攤出，逐項請使用者決定採納或不採納。** 可以補上該項對應的程式位置等事實，但**不替使用者下「這項成立／不成立」的結論**——寫出這段程式碼的 session 判斷不了自己哪裡錯，這正是請冷眼的原因。
- 採納要修的，修正走 commit 關卡；全部提交後**回到驗證整段重跑**，再停一次。
- **審查不自動重跑。** 修正後要不要再審一次，由使用者決定。
- 使用者的採納與不採納（含理由）記下來，定稿時寫進 ticket 的審查紀錄。

### 定稿

使用者在停點回「繼續」後一路做完，不再停：

1. **把核對結果寫回 ticket** —— 見下方「寫回 ticket」。
2. **回報** commit 清單（含各自的 commit message，包含跨層收斂與停點之後的修正 commit），以及寫回 ticket 的結果。

### 寫回 ticket

**核對結果必須留在 ticket 檔案裡，不能只出現在對話中。** 對話會被清掉，ticket 是這張票唯一的長期紀錄；只留在 session 裡的核對，等於沒做過。

做兩件事：

**一、勾選達成的驗收條件。** 判定為「達成」或「經裁示調整」的，把該條 `- [ ]` 改為 `- [x]`；移交、部分達成與未達成維持 `- [ ]`。**只改 checkbox 狀態，條文一字不動。**

**二、在 ticket 末尾 append 一份帶證據的核對表。**

```md
## 驗收核對（YYYY-MM-DD）

| # | 判定 | 依據 |
| --- | --- | --- |
| 8 | 達成 | `DmsDeviceMovementService.Query()`；TestDmsDeviceMovementService.查詢僅納入確認狀態的工單 |
| 12 | 達成 | `Query()` 全程以 IQueryable 組條件，未先 ToList 再過濾 |
| 14 | 經裁示調整 | 使用者裁示錯誤訊息不帶倉庫名稱，與其他工單一致；實際數量已帶出 |
| 15 | 移交 05 | 詳細頁的可視範圍由 05 的驗收條件承接；列表端已實作於 `GetListData` |
| 17 | 部分達成 | 下拉已實作，缺「退貨單」選項 |
| 19 | 未達成 | 權限攔截的整合測試未寫 |

未完成項目：#17、#19
移交項目：#15 → 05

本票 Test Consolidation：刪除 2 支僅為逼出 RED 的鷹架測試（行為由 `TestXxx.查詢僅納入確認狀態的工單` 守著）；3 條同質 case 併為 `TestXxx.各狀態的顯示文字` 一支參數化測試。

冷眼審查（YYYY-MM-DD，fixed point a1b2c3d）：Spec 2 項、Standards 3 項；採納 2 項（`fix: 刪除端點補上權限檢查`）；不採納 3 項（Feature Envy ×2 沿用模組既有寫法、Primitive Obsession 單據編號全專案皆為字串）。
```

規則：

- **`#` 用驗收條件在該 ticket 內的出現順序。**
- **「依據」欄不得留空，也不得只寫「已實作」。** 要寫得出程式位置或測試名稱——**光打勾等於沒寫**，半年後回頭看一排 `[x]` 而不知道它靠什麼成立，這份紀錄就白留了。
- **只列有意義的內容，不逐條複製驗收條件原文** ——原文就在上面幾行，重抄一次是純膨脹。
- 重複執行時（例如補做未完成項目後再跑一次收尾）**就地更新同一份表**，不要 append 第二份。
- **本票有做 Test Consolidation 時，在表格後補一行摘要**（刪／併了什麼、該行為現在由誰守，含跨層重複檢查的刪併），依據是 `implementation-rules.md` 的「邊做邊記」累積的內容。**一行帶過整張票，不逐 commit 流水帳**——逐筆紀錄 git history 已經有了，這裡要的只是讓半年後讀 ticket 的人看得出「測試變少是刻意收斂，不是漏測」。本票沒刪沒併就整行不寫，不要留一句「無」。
- **本票有跑冷眼審查時，再補一行審查紀錄**：日期、fixed point、兩軸各幾項、採納哪些（帶修正 commit 的 message）、不採納哪些與理由。不採納的理由是這行最有價值的部分——之後的人看到同一段程式碼會冒出同樣的疑問。沒跑審查就整行不寫。

### 收尾**不做**什麼

以下一律不做，發現疑慮只記錄、不判定：

- **不判斷有沒有做多餘的事（scope creep）。**
- **不判斷實作是不是錯的。**
- **不評程式碼品質、重複、命名。**

理由：收尾由**寫出這段程式碼的同一個 session** 執行。它能可靠回答「我做了什麼」（回憶），但不能公正回答「我做得對不對」（判斷）——它剛剛才確信自己是對的。這三件事需要沒看過產生過程的冷眼，也就是上面的冷眼審查。

**驗證與定稿一律在本 session 內完成，不得開 sub-agent。** 收尾若開 sub-agent，成本結構就等同 `/code-review`，卻沒有它的獨立性。

### 發現問題時不要就地修

驗證階段測試失敗、或有驗收條件部分達成或未達成時：**不要靜默修掉再 commit**。把驗證做完，在停點攤出問題與影響，由使用者決定處理方式。使用者沒有看過的修改不該進 repo，那會破壞前面每個 commit 都經過確認的保證。
