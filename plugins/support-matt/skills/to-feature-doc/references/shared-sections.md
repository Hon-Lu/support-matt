# 共用章節寫法

`to-feature-doc` 的 final 與 `to-handoff-doc` 共用的章節與格式。這些章名與順序是團隊共用的骨架，章內依專案需求取捨。

## 背景與問題

寫調整前的現況與問題、為什麼要改、改完解決什麼，3-8 行起跳。問題不只一個時用 ①②③ 編號。既有做法被取代時，附一張改前／改後對照表。

## 影響

沿用「背景與問題」的編號，寫每個問題不處理的後果。受影響的對象不只一個（App、合作方、其他系統）時，改用「對象／影響」表。

## 來源與範圍

- **來源**：需求單、PRD、前一階段 Issue 的連結，定案的決議帶日期。
- **所屬模組**與 **Schema**（無變更，或指向寫它的功能章）。
- **範圍**用下表。「不包含」只列讀者可能誤以為包含的項目，說明欄必須有內容。

| 類型 | 項目 | 說明 |
| --- | --- | --- |
| 包含 | <功能> | 一句白話寫出改了什麼，指向功能章 |
| 不包含 | <讀者可能誤以為包含的項目> | 為什麼不含，或它現在怎麼運作 |

## 相依與上線

收相依的 Issue 與系統、上線順序、回滾限制。只收上線時要有人採取行動、或跨功能才看得出來的事；某個功能自己的行為變化放回該功能。

用一張表：項目、要做什麼、不做的後果。先後順序本身就是規則時，改用編號清單，並寫出順序顛倒的後果。

## 待確認事項

每項寫出問題與要問誰（人或角色）。

## `BR-xx` 格式

```md
#### BR-xx <規則標題>
**規則**：一句話。
**判定**：條件與結果。兩個以上條件用判定表；有分支的判斷流程用流程圖；錯誤訊息寫原文；檢查順序重要時寫一句順序。
**理由**：為什麼這樣定，包含被排除的做法與排除原因。
```

`BR-xx` 全文連續編號，依出現順序，不因分章而重新起算。

## 併發保護

「設計」寫併發保護時，逐一點名這個功能寫入的每一份共用資料（例如被綁定的設備，以及綁定者本身那一列），各自寫出被兩個操作同時改時由什麼擋住、失敗的一方看到什麼。只寫了其中一份，讀者無從判斷其他份有沒有被保護。查程式碼找不到保護的，寫進「待確認事項」。先後順序或併發會影響結果時，附一張循序圖。

## 用圖

有分支的判斷流程、順序本身就是規則的參與者交互、三態以上的狀態轉換，用文字敘述讀者得自己在腦中畫圖，這時用 mermaid 畫出來：判斷與分支用流程圖（`flowchart`），參與者之間的時序用循序圖（`sequenceDiagram`），狀態轉換用狀態圖（`stateDiagram-v2`）。

循序圖只在先後順序或併發會影響結果時畫，例如讀取後被其他作業改掉要擋下、檢查必須排在寫入之前、換綁要先處理舊的再處理新的。一般的「頁面 → 服務 → 資料庫」呼叫鏈用文字帶過。

- **一張圖只講一件事**，業務判斷與實作步驟分開畫；本次沒動的既有檢查不畫進去。
- **圖與表各負責不同的資訊。** 條件少、沒有分支的對照（例如「原狀態 → 處理方式」）用判定表就夠。
- **線性流程用文字。**

圖放在它說明的那一段旁邊：判斷流程放在該 `BR-xx` 的「判定」，參與者的交互放在該功能的「設計」。
