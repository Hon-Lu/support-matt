# to-handoff-doc

維護單一份 `handoff-doc.md`：規格完成後交給別人實作，貼上公司**主 Issue**。讀者是拿到文件就要開工的工程師，不使用 Matt 工作流，也沒有參與討論。

與 `to-feature-doc` 的差別只有**由誰實作**。那支在實作後由既成事實組裝；本 skill 在動工前寫，沒有程式碼可以抄，所以每個落點都要實際查過，並標明哪些必須遵守、哪些可以調整。

## 工作流位置

```text
grill-with-docs → to-spec → [to-handoff-doc] → to-gitlab-issue → 實作者開工
```

Matt 的前半段（grill、`to-spec`，需要時加 `research`、`prototype`、`domain-modeling`）負責把事情想清楚，與誰實作無關，照常使用。`to-tickets`、`implement-stepwise`、`to-acceptance-map` 不走：實作者不用票，驗收基準是本文件的「驗收條件」。

## 核心規則

- **一個 feature 一份 `handoff-doc.md`，一律就地修訂。**
- **`spec.md` 是需求權威。** 需求不明時停下來請使用者改 `spec.md`；本文件只承接需求。
- **文件自足。** 讀者手上只有這一份，需要的需求內容、錯誤訊息原文、邊界值與預設值都內嵌進文件，不留 `spec.md`、User Story、ADR、ticket、skill 名稱、`.scratch/` 路徑或其他開發流程用語。
- **實際查過才寫。** 文件點名的既有 API、資料表、類別都要在程式碼裡查到，不臆造欄位、契約、權限或業務規則。
- **寫到能開工就停。** 必須遵守的寫清楚，其餘留給實作者判斷；寫太細會隨程式過期，也會逼實作者照抄。
- **不拆 ticket、不寫程式、不跑測試、不建立或修改任何遠端 Issue。**

## 檔案位置

`.ai/.scratch/<feature-slug>/handoff-doc.md`，與 `spec.md` 同目錄。實際根目錄依 `.ai/docs/agents/issue-tracker.md`；找不到時改讀 `docs/agents/issue-tracker.md`。

## 模式

由文件是否存在自動判定，使用者也可明確指定：

| 模式 | 何時 | 產出 |
| --- | --- | --- |
| **建立** | `handoff-doc.md` 不存在 | 完整文件，頂部 `文件狀態: draft (YYYY-MM-DD)`，確認後改為 `ready` |
| **修訂** | 文件已存在 | 就地改，在「附錄：修訂紀錄」追加一列 |

`ready` 代表可以開工：沒有會阻擋開工的待確認事項。修訂後仍有阻擋項時，狀態退回 `draft`。

需求有變時，先請使用者改 `spec.md`，再回本 skill 修訂。`to-change-request` 服務有票的開發流程，這裡用不上。

## 前置讀取

1. `.ai/docs/agents/issue-tracker.md`，兩處皆無則請使用者先跑 `setup-matt-preset`。
2. `.ai/docs/agents/domain.md` 指出的專案詞彙表與 ADR，命名與既有決策的依據；檔案不存在時略過。
3. `spec.md`，**必要**。不存在時停下來，請使用者先跑 `to-spec`。

## 流程

### 1. 查程式碼

讀 `references/codebase-discovery.md` 後查找。完成條件：`spec.md` 的每條 user story，都知道由哪個既有元件承接，或確定要新增。

### 2. 掃過全部資訊面向

系統邊界 ／ 角色與權限 ／ 狀態與動作語意 ／ 使用者介面 ／ 業務規則 ／ 模組責任 ／ 對外契約 ／ persisted data 與 schema ／ 交易、併發與存取代價 ／ 相容性與 rollout ／ 既有資料在新規則下會怎樣 ／ 範圍外仍走舊邏輯的路徑。

每項的結論是：**寫在哪個功能章的哪一段** ／ **寫在相依與上線** ／ **不適用，不寫**。結論寫在回報。動到 persisted data 時，對照 `../to-feature-doc/references/data-design-checklist.md`。

### 3. 釐清

有疑問時讀 `references/clarification-and-open-questions.md`，一次問一到三個會改變文件的問題。

### 4. 組裝

寫技術內容前讀 `references/constraint-levels.md`，寫共用章節前讀 `../to-feature-doc/references/shared-sections.md`。

```md
# <標題>

文件狀態: draft (YYYY-MM-DD)

> **開工前置**：<必須先完成或先上線的項目，一兩句，指向「相依與上線」。沒有就整行不寫>

## 背景與問題

## 影響

## 來源與範圍

## 處理方式

標「設計決策」的內容必須遵守，要改請先提出。標「實作方向」的內容可以調整，請在 MR 說明原因。

### <功能一>
### <功能二>
…

## 驗收條件

## 相依與上線

## 待確認事項

## 附錄：修訂紀錄
```

`背景與問題`、`影響`、`來源與範圍`、`處理方式`、`驗收條件`、`附錄：修訂紀錄` 固定存在；其餘有內容才寫。只有一個功能時省掉功能這一層，下列區塊直接用 `###`。

#### 功能章

| 區塊 | 只回答 | 何時需要 |
| --- | --- | --- |
| 開頭結論段（不開小節） | 為什麼改、主要改了什麼 | 每章都有 |
| `#### 行為` | 使用者或呼叫端看到什麼、操作後有什麼結果 | 有畫面、操作或輸出要描述 |
| `#### BR-xx <規則標題>` | 什麼條件成立、怎麼判定、失敗怎麼處理、為什麼 | 有需要判定的業務規則 |
| `#### 設計` | 必須遵守的契約、資料、交易與責任分界 | 有改了會接不上或破壞一致性的內容 |
| `#### 實作方向` | 建議的落點、可沿用的元件、資料流 | 有值得實作者知道的既有模式 |
| `#### 對既有的影響` | 與調整前不同、讀者可能意外的地方 | 既有資料、舊檔或既有操作的結果有變 |

簡單的功能不拆小節。區塊之間講同一件事時，只留一處。

有先後相依時，在 `## 處理方式` 最後加 `### 建議實作順序`，寫哪些要先做、為什麼。

#### 程式名稱

- API 路徑、欄位、狀態碼、資料表、設定旗標寫原文。
- 既有的類別、方法、檔案照原名引用，讀者才找得到；不寫行號，行號很快會過期。
- 本次新增的內部元件寫責任，名字留給實作者，規則見 `references/constraint-levels.md` 的「命名」。

#### 驗收條件

用勾選清單，功能多時依功能或「回歸」分組。

```md
- [ ] `EncodeType = 2` 或 `abc` → 回 `ResultState_M5`
- [ ] 不帶 `EncodeType`、原有欄位放原文時，回應與修改前相同
```

- 每條寫出條件與預期結果，能判斷成立與否；錯誤碼與錯誤訊息寫原文。
- 涵蓋正常、邊界、失敗與不該改變的既有行為。
- 每條 `BR-xx` 至少有一條對應。指不回任何行為或規則的條目是新需求，停下來請使用者先改 `spec.md`。

#### 待確認事項

共用寫法之外，會阻擋開工的項目在開頭標 **【阻擋開工】**。

#### 附錄：修訂紀錄

欄位為「日期、改了什麼、為什麼」，第一列是建立文件。

### 5. 送出前自檢

**自足**
- 沒有 `spec.md`、User Story、ADR、ticket、skill 名稱、`.scratch/` 路徑、TODO 與內部工作註記。

**可開工**
- 只讀一個功能章，就知道要做的行為、規則與必須遵守的設計。
- 文件點名的既有 API、資料表、類別都查到了。
- 至少有一條實作方向；全部寫成硬約束時，回頭看哪些只是施工偏好。

**可驗收**
- 每條驗收條件都判得了成立與否，每條 `BR-xx` 都有對應。
- 「背景與問題」的每個編號，「影響」都有對應的後果。
- 待確認事項每項都寫了要問誰，阻擋開工的都有標記。

### 6. 確認與回報

把整份攤給使用者，**逐條確認「驗收條件」與標了「設計決策」的內容**，其餘章節請使用者掃過。確認後，沒有阻擋開工的項目就把狀態改為 `ready (YYYY-MM-DD)`。

回報第 2 步各面向的結論（含判定為不寫的項目與理由）與仍未結的待確認事項。下一步提示使用者：

```text
/to-gitlab-issue <Issue URL>
```

## 衝突處理

`spec.md`、ADR、程式碼現況互相矛盾時，**停下來**，把雙方原文各引一句請使用者裁決，不得自行選邊。使用者選擇暫緩時，列入「待確認事項」並註明衝突的另一方在哪。

## 下一步引導（純提示，不主動調用）

`ready` 之後由使用者調用 `to-gitlab-issue` 發布。發布後文件有修訂，回本 skill 修訂，再重新發布。
