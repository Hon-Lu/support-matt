# 反問與待確認事項

出現任何疑問或不明確之處時讀本文件。本 skill 對模糊需求採取**主動暫停並反問**，而非自行假設。

## 先確認「該不該問」

本 skill 位在 `grill-with-docs` 與 `to-spec` 之後。使用者已經被盤問過一輪了，**再問一次同樣的事情是浪費**，也會讓人懷疑前面那輪白做。

問之前先跑三個檢查：

1. **`spec.md` 或當前對話有沒有答案？** 有 → 引用它，不問。
2. **程式碼能不能回答？** 能 → 自己查，不問。ADR 與專案詞彙表同理。
3. **我能不能合理判斷、並承擔被推翻的風險？** 能 → 做出決策，寫成設計決策並附理由，不問。

三個都否，且**缺少的東西會影響需求理解或重大設計**，才問。

**「能自行判斷」不等於「可以自己編」**：資料表欄位名稱可以自己取（設計決策），但「這個欄位到底要不要存歷史值」若牽動業務語意，就要問。

## 必須立即停下來提問的情況

出現以下任一情況時，**立即停止撰寫並向使用者提問**，取得明確回覆後才繼續：

- 需求語意有多種解讀，而不同解讀會產生不同的狀態機或不同的資料模型。
- 邊界不清晰：不確定某職責、組件、資料或流程是否屬於本次範圍。
- 角色、權限、業務規則、狀態流轉或預期行為無法從 `spec.md`、ADR 或程式碼確認。
- 任何會實質改變範圍或架構的判斷。
- 驗收條件寫到一半發現**某條指不回任何 user story 或 `BR-xx`**——那是新需求，停下來請使用者先改 `spec.md`。
- 資料來源、資料流或資料寫入責任不明。
- 錯誤處理、重試、冪等或一致性策略無法判斷。
- **`spec.md` 與本文件、ADR 或程式碼互相衝突**——見 SKILL.md 的「衝突處理」。

禁止以「先假設一個方向繼續做」或「這部分之後再說」的方式略過。

## 提問風格

- 一次提出一到三個重點問題，聚焦在會改變文件的關鍵點。
- 盡可能提供具體選項。
- 僅在 `spec.md` 或程式碼強烈暗示某一方向時，才標記建議答案。
- 簡短說明答案會如何影響文件——講清楚它會動到哪一章。
- 問衝突時，把雙方原文各引一句，讓使用者不必自己去翻。
- 待疑問解決、或經使用者同意記錄為待確認事項後，才繼續起草。

## 「待確認事項」的彙整

凡是曾被跳過、暫緩討論、或尚未達成共識的問題，一律完整彙整至「待確認事項」章節，不得遺漏或省略。這包含：

- 經提問後，使用者選擇暫緩或跳過的問題。
- 提問後仍未達成共識、或回覆不足以定案的事項。
- 需由特定角色（需求方、PO、工程審查）後續回答的開放問題。
- 程式碼查找中發現、無法憑現有資訊裁決的落差或模糊點。
- **尚未裁決的文件衝突**——此時該列要註明衝突的另一方在哪。

此章節只收確實缺少必要資訊、且無法由 `spec.md`、現有程式碼或使用者補充合理推導的項目。

每個待確認事項寫清楚：問題是什麼、會影響哪個設計判斷、要問誰。會阻擋開工的標 **【阻擋開工】**。

無未解問題時整章不寫。

## 修訂處理方式

使用者回答「待確認事項」中的問題時：

- 將確認的答案寫入對應章節，只寫一處，並從「待確認事項」移除該項。
- 若該答案原本是暫定的設計決策，且使用者確認了不同方向，更新該處內容，被推翻的方案寫進理由。
- 若答案屬於需求、範圍或行為，請使用者更新 `spec.md`，本文件只同步受影響的章節與驗收條件。
- 若答案是判準、邊界值、錯誤訊息文字，直接寫進「驗收條件」。
- 無問題剩餘時整章移除（含標題）。
