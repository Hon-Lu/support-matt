# to-issue-doc

維護單一份 `issue-doc.md` —— 貼上公司**主 Issue** 的規格文件，拆票的 issue 放在它的 comments。

## 這支 skill 的取捨（先讀這段）

一份規格文件混了兩種東西，它們的最佳寫作時機相反：

| 內容 | 最佳時機 | 理由 |
| --- | --- | --- |
| 驗證條件 `VC-xx`、範圍邊界、關鍵決策 | **拆票前** | 它們是**約束**：拆票本身就是設計行為，落點與邊界沒先定版，決策會發生在拆票裡而沒有紀錄 |
| 系統分析、資料模型、介面與流程、實作落點 | **實作後** | 它們是**紀錄**：程式碼就是答案，事前寫是猜，事後抄才準 |

因此本 skill 把文件切成兩個時點寫，而不是一次寫完：**brief 只寫上排，final 才寫下排**。

**輕量只屬於開發中。** brief 輕，是為了開發途中修訂便宜、不拖住 Matt 的開發流；final 的交付物是主 Issue 的 SA/SD，**完整度與 `to-engineering-spec` 定稿相同**，而且直接沿用它的文件模板與章節存在門檻。兩支 skill 的差別只在**設計什麼時候定版**：那支在動工前一次寫到位，適合設計必須先審查的重案；本 skill 在實作後由既成事實寫，一般案子用它。

**文件的長短由章節去留決定，不由內容壓縮決定。** 沒動到的面向（例如權限、狀態機、schema）整章不寫；動到的面向寫到定稿標準，不因為整份文件比較小就跟著縮寫。

## 工作流位置

```text
grill-with-docs → to-spec → [to-issue-doc brief] → to-tickets → implement-stepwise
                                    ↑                                          ↓
                    [to-issue-doc 修訂] ← to-change-request           全部 ticket 完成
                                                                               ↓
                      貼上主 Issue ← to-acceptance-map ← [to-issue-doc final]
```

**brief 在 `to-tickets` 之前，不是之後。** 兩個理由，都與「順手」無關：

- **拆票是設計行為。** 要把功能切成有相依順序、各自可獨立完成的切片，必須先決定落點：沿用哪些既有機制、資料寫入責任在誰、新邊界畫在哪。brief 放在拆票之後，不會讓這些決策不發生，只會讓它們**發生在拆票裡、沒有紀錄、沒有經過使用者確認**，而票是 `implement` 唯一實際吃的東西。
- **`VC-xx` 不能被票錨定。** `to-acceptance-map` 明訂驗證基準不得來自 ticket，且 feature 層級盤點的存在理由，正是回收那些任何單張票都看不到的條目（否定式約束、跨切片一致性）。看著票寫 VC，最可能的結果不是寫錯，而是變成「各票驗收條件的並集」——每條都合理、沒有任何症狀，卻剛好丟掉這張表唯一不可取代的部分。

沒有票在手時 `VC-xx` 照樣判得動，判的是條目性質不是切分方式，見「驗證條件」一節的四類判準。漏收由 `final` 的校準兜底。

**`final` 必須在 `to-acceptance-map` 之前跑。** `to-acceptance-map` 拿本文件的 `VC-xx` 當唯一驗證基準，而 `final` 的第一件事就是依實際交付校準那張表；順序反過來，盤點的是開發前的舊基準。

## 核心行為規範（最高優先）

- **一個 feature 一份 `issue-doc.md`，一律就地修訂。** 不產 `-v2`、不另存交付版副本、不建立第二份取代文件。
- **本文件的章節清單是資訊檢查表，不是 heading 檢查表。** 每個資訊面向都**必須被思考**，但思考完的結論可以是「值得獨立成章」「併入相鄰章節」「一句話帶過」「完全無資訊增量，不寫」。**不要用空章節或「本次無」證明自己檢查過**——檢查的痕跡寫在回報訊息裡，不寫進文件。反過來也成立：**省略 heading 不等於省略分析**，沒開「資料模型」章之前，schema／索引／關聯有沒有動仍然要查過。
- **章節依當下情況動態去留，內容不壓縮。** brief 依下方的 brief 模板；final 依 `to-engineering-spec` 的章節存在門檻。單表 CRUD 不該長出跟跨模組交易改造一樣的目錄；但進得了門檻的章節，內容寫到定稿標準，不為了讓文件變短而併章或縮成一句。
- **只有 `VC-xx` 那張表需要使用者逐條確認**，其餘章節攤出來讓使用者看一眼即可。確認關卡越多，這支 skill 就退化成它要取代的東西。
- **brief 不寫實作後才知道的事。** 介面簽章、欄位級 schema、方法落點一律留給 `final`。寫不出來就是還不該寫，不要用猜的填滿模板。
- **final 只寫既成事實。** 來源是程式碼、ticket 的驗收核對表與 `git diff`，不是 brief 的計畫。與 brief 不一致的地方**明確列出來讓使用者裁決**，不得靜默以 brief 為準覆蓋事實，也不得靜默以事實覆蓋 brief 而不提。
- **開發期間，需求的權威是 `spec.md`。** 本文件寫不下去是因為需求不明時，停下來請使用者改 `spec.md`（或走 `to-change-request`），不要在本文件裡自行發明需求。
- **final 是自足、給人讀的交付快照。** `spec.md`、ADR 都不會貼上 GitLab，final 不得引用它們（連結、User Story 編號、ADR 編號、「詳見需求文件」都不行），也不留任何開發流程的用語；需要的內容一律內嵌進業務規則與功能介面。brief 與修訂模式可以引用，因為那時的讀者是 agent。
- **不拆 ticket、不寫程式、不跑測試、不盤點測試覆蓋、不建立或修改任何遠端 Issue。**

## 不隨複雜度變動的部分

以下幾樣是跨文件、跨 skill 的追溯基礎，**任何模式、任何規模都固定存在，不得因為「收斂」而合併或省略**：

1. **標題與文件狀態行** —— `文件狀態: brief | final (YYYY-MM-DD)`，模式判定與續作判定都吃它。
2. **`## 驗證條件` 章與 `VC-xx` 編號** —— 一章、一張表、一組編號。`to-acceptance-map` 唯一的驗證基準，章名不得改寫、不得拆成多張表、不得把條目散落到其他章節。
3. **範圍** —— brief 為 `## 目標與範圍`，final 為模板的 `## 範圍與非範圍`。做什麼、不做什麼是讀審的人最先看、最會誤會的東西，再小的案子都要有。
4. **修訂紀錄** —— **有修訂才出現**，同一階段內不刪列、不合併。brief 為 `## 修訂紀錄`，記開發中途的改動；**轉成 final 時不帶過去**（改動已反映在各章現況）。final 之後的修訂記在 `## 附錄：修訂紀錄`。
5. **`## 已知限制`** —— **有已接受的限制才出現**。`to-acceptance-map` 依章名讀它，章名不得改寫。

其餘所有 heading 都是**候選章節**：brief 依下方的 brief 模板，final 依 `to-engineering-spec` 的章節存在門檻，決定它這次要不要成為獨立 heading。

## 檔案位置

`.ai/.scratch/<feature-slug>/issue-doc.md` —— 與 `spec.md`、`issues/` 同目錄。實際根目錄依 `.ai/docs/agents/issue-tracker.md`；找不到時改讀 `docs/agents/issue-tracker.md`。

## 三種模式

由文件狀態自動判定，使用者也可明確指定：

| 模式 | 何時 | 產出 |
| --- | --- | --- |
| **brief** | `issue-doc.md` 不存在 | 一頁 brief，頂部 `文件狀態: brief (YYYY-MM-DD)` |
| **修訂** | 文件存在且狀態為 `brief`，開發尚未結束 | 就地改，追加修訂紀錄 |
| **final** | 全部 ticket 完成（含 `to-change-request` 之後插入的新票） | 校準 VC + 依 `to-engineering-spec` 模板由既成事實重新組裝成 SA/SD，狀態改為 `final (YYYY-MM-DD)` |

狀態已是 `final` 又被調用時，停下來確認：這是同一條 branch 的續作（確認後退回 `brief` 再修訂），還是該開新的 feature？**不要在 final 文件上靜默續改。**

## 前置讀取

1. `.ai/docs/agents/issue-tracker.md`（找不到改讀 `docs/agents/issue-tracker.md`）—— 檔案位置與慣例。兩者皆無則請使用者先跑 `setup-matt-preset`。
2. `.ai/docs/agents/domain.md` 指出的 `CONTEXT.md` 與 ADR —— 命名與既有決策的依據；檔案不存在時**靜默略過**。
3. `spec.md` —— 需求權威。**brief 與 final 模式必讀**：final 要把需求內嵌進業務規則與功能介面。
4. `issues/` 下的 ticket（含驗收核對表）—— **final 模式必讀**；brief 模式時尚未拆票，不存在。
5. `to-engineering-spec` 的 `references/document-template.md` 與 `references/writing-rules.md`（相對本 skill 為 `../to-engineering-spec/references/`）—— **final 模式必讀**：SA/SD 的章節結構、章節存在門檻、行數預算與寫作規則都以它們為準，本 skill 只列差異。動到 persisted data 時，再讀同目錄的 `data-design-checklist.md`。

命名一律使用 `CONTEXT.md` 的領域詞彙；與既有 ADR 抵觸時明確指出，不默默覆蓋。

## brief 模式

在 `to-spec` 之後、`to-tickets` 之前執行。目標是**十分鐘寫完、讀審的人看得懂你要做什麼**，而且**拿得去拆票**。brief 不是縮小版的技術設計，別把它寫成 mini engineering spec。

下面五個是候選章節。`目標與範圍` 與 `驗證條件` 固定要有；另外三個**有內容才寫，沒有就整章不出現**——不要留「本次無」佔位。

```md
# <功能名稱>

文件狀態: brief (YYYY-MM-DD)

## 目標與範圍
本次要解決的問題 2-4 行。接著兩個清單：**範圍內**、**明確不做**。
「明確不做」比「範圍內」更值錢——它是讀審的人最會誤會的地方。

## 方案輪廓
打算怎麼做，讓沒讀過程式碼的人也判斷得出方向對不對：
主要參與的模組／服務、資料從哪來到哪去、既有機制沿用哪些、新增哪些。
5-10 行，或一張流程／對照表。
**不寫介面簽章、不寫欄位級 schema、不寫方法落點**——那些是 final 的事。

## 關鍵決策
一行一條，附一句取捨理由。3-5 條，通常來自 grill 的結論。
難以回復、影響超出本 feature 的，另外開 ADR 並在此指過去。
只有一條決策時，直接併進「方案輪廓」，不開獨立章。

## 驗證條件
見下方「驗證條件」一節。這是本文件唯一需要逐條確認的表。

## 風險與待釐清
**只放還沒解決的**：尚未拍板的問題、需要 owner 決定的事、上線後要追蹤的。
沒有 open 項目就整章不寫，不要留「無」。
```

寫完後把整份攤給使用者，**只針對 `VC-xx` 那張表請他逐條確認**；其餘章節請他掃一眼有無明顯錯誤。確認完成即停止，並在回報中給出可直接貼的下一步：

```text
$to-tickets 依 .ai/.scratch/<feature-slug>/spec.md 與 .ai/.scratch/<feature-slug>/issue-doc.md 拆票，並參照 .ai/docs/adr/ 與 .ai/CONTEXT.md
```

**`方案輪廓` 與 `關鍵決策` 就是拆票的輸入**，因此那一行要帶上本文件；`$to-tickets ...` 只出現在回報訊息，不寫進文件。

## 驗證條件（`VC-xx`）

**一章、一張表、一組編號，是整份文件的總驗收條件**，也是 `to-acceptance-map` 唯一的驗證基準。

**VC 定義「要證明什麼」，測試決定「怎麼證明」。** 每條 VC 回答「什麼結果必須成立，才算這個需求完成」；用哪些測試、在哪一層、斷言什麼，是測試的事——一條 VC 可以由多支測試共同證明，一支測試也可以同時證明多條。條文裡寫進去的每個名詞，盤點時都會被當成要證明的範圍，所以條文只放前兩種東西：

| 寫進條文 | 不寫進條文 |
| --- | --- |
| 需求本身的範圍：依據點名的入口、對象、情境 | 等價類的展開：同一條規則下的各個狀態、類型、輸入值 |
| 對外可觀察的結果：資料、畫面、回傳、有沒有產生紀錄 | 驗證手段：測哪一層、怎麼準備資料、斷言什麼、步驟順序 |
| | 內部機制用語：「交易回滾」「重新查詢」——改寫成它保證的結果，例如「無部分寫入」（第一關第四類的實作路徑約束除外） |

反過來也不能寫到判不了真偽：「匯出結果正確」沒有說要成立什麼。範圍本身就是需求時——例如兩個入口必須一致——入口要寫出來。

寫這張表要連過四道關卡，順序不能換：**歸屬**（該不該進來）→ **強度**（有沒有超出依據）→ **可終結**（判不判得完）→ **量級**（是不是太多）。前兩道決定表裡有哪些條目，後兩道決定每條長什麼樣。**四道關卡的共同特徵是：沒過關的條目在本文件裡完全沒有症狀**——每條單看都合理、都可判斷真偽，要到 `to-acceptance-map` 才會變成一整排「覆蓋不足」。所以要在這裡逐條跑，不能靠讀起來順不順。

### 第一關：歸屬——該不該進來

> **這條若沒過，有沒有任何單一 Ticket 會發現？會，就不要寫進來。**

欄位必填、錯誤訊息原文、格式、預設值、選項連動、分頁筆數、排序方向——開票當下就驗掉了，寫進來不增加任何保護，只會讓這張表隨欄位數量無限膨脹。**這是本章最大的失控模式**，而且每一條單看都合理、都可判斷真偽，粒度檢查完全攔不住。

留下來的是**沒有任何單一切片看得到的東西**，就是下面這四類：

1. **跨切片的一致性** —— 同一取值在顯示、篩選、排序三處一致；查詢與匯出得到相同結果。
2. **整條規則的最終效果** —— 各票各做一段，合起來是否真的達成該業務規則要求的結果。
3. **權限的實際攔截** —— 不是畫面有沒有藏按鈕，是後端擋不擋得住。
4. **對實作路徑的要求** —— 但**只收已經寫進「關鍵決策」的那些**，見下一小節。

**這四類判得動不需要有票在手**——判的是條目的性質，不是切分方式；票在手上只會讓它更省力。反過來說，寫 brief 時看不到票是**好事**：否定式的約束（「未使用 X」「未產生 Y」）在票裡沒有影子，盯著票寫必然漏掉它們，而那正是這張表唯一不可取代的部分。

#### 第四類是最窄的一類，不是最方便的一類

第四類天生沒有可觀察的行為，`to-acceptance-map` 對它幾乎只判得出「不適用測試」或「覆蓋不足」。所以它的門檻要比其他三類更高，**兩個條件同時成立才收**：

1. **該約束本身已經寫進「關鍵決策」章**——VC 只負責寫「怎麼驗證那條決策成立」，不負責發明它。
2. **違反它會造成使用者觀察不到、但不可接受的後果**——例如資料外洩、既有機制被繞過。

**沒被寫成關鍵決策的實作要求一律不進本表**：隨手寫出來的 N+1、要不要 eager load、共用哪個 helper、繼承結構、方法名，那些是 coding standard 與 code review 的事。寫進規格既擋不住也追不了，還會讓文件被下一次 refactor 弄成假的。這與 `to-engineering-spec` 的判準一致。

真的收進來的那幾條，也要寫成**可觀察的性質，不是目前的實作形狀**：

| 寫法 | 判定 | 理由 |
| --- | --- | --- |
| 列表與匯出在同一組篩選條件下結果一致，且不受分頁影響 | 寫成 VC | 可觀察，refactor 後仍該成立 |
| 列表與匯出必須共用同一個 `BuildQuery` 方法 | 不寫成 VC | 綁死方法名，那只是達成上一條的其中一種手段 |
| 沿用既有權限檢查機制，不自建第二套判定路徑（已列為關鍵決策） | 寫成 VC，`驗證方式` 填 `讀程式碼` | 決策已拍板，繞過的後果使用者看不到 |
| 清單載入不得對每列各發一次查詢 | 除非效能上界已是關鍵決策，否則不寫 | 一般情況屬 code review 的事 |
| 匯出模型必須繼承 `ExportData` | 不寫成 VC | 綁死繼承結構，換掉不影響任何可觀察行為 |

### 第二關：強度——不得超出「依據」欄

**過頭的條文是最難自己發現的失控**：每個字單看都對，但它要求的範圍比 `spec.md` 真正要求的大。它不會被歸屬判準攔下（性質確實是跨切片的），也不會被粒度檢查攔下（就是一句話），最後在盤點時變成永遠補不完的覆蓋不足。

三種典型的放大：

| 放大形式 | 例 | 收法 |
| --- | --- | --- |
| **未列舉的複數** | `spec.md` 只講了列表與匯出，VC 寫「同一取值在各處一致」 | 列明是哪幾處——列的是依據點名的範圍，不是等價類（見第三關） |
| **補上的全稱量詞** | `spec.md` 講的是某個情境，VC 寫「任何情況下都不得…」 | 把情境寫回前提 |
| **順手升級的強度** | `spec.md` 說「預設不顯示」，VC 寫成「不得取得」 | 依 `spec.md` 的用詞，不自行加碼 |

檢查法：**把該條與 `依據` 欄指到的那句話並排，問「依據那句話沒說到的東西，這條有沒有多要求？」** 多要的部分二選一——回 `spec.md` 補成正式需求（走 `to-change-request`），或從 VC 拿掉。**不得留在表裡當隱形需求**：那是在用驗證條件擴充需求範圍，而本 skill 沒有這個權限。

### 第三關：可終結——真偽判得了、範圍有邊界

`to-acceptance-map` 判「覆蓋不足」，要舉得出一個能通過現有測試、卻違反條文的合理實作。條文含開放式或複合式條件時，這種反例永遠舉得出來——不是測試寫得不夠，是**條文本身沒有終點**。

寫完每條問兩次：

> **這條的範圍邊界在哪？答不出來，就重寫。**
>
> **條文列出的值，是各自不同的要求，還是同一條規則的等價類？**

| 寫法 | 判定 |
| --- | --- |
| 停用的項目不出現在清單、搜尋結果與匯出檔 | 可終結——範圍列明了 |
| 停用的項目不出現在任何取得資料的地方 | 不可終結——列明範圍，或拆成各自一條 |
| 逾期單據自動結案，並通知關係人、寫入稽核紀錄 | 複合——三件事三條，或只留真正跨切片的那件 |
| 狀態為草稿或退回的單據可再編輯（兩者同屬「未送審」） | 等價類被列舉——寫成規則本身「未送審的單據可再編輯」 |

**同一條規則的多個等價類不各寫一條，也不在一條裡列舉。** 括號裡的狀態清單、「為 A 或 B 時同樣…」都是列舉；寫進條文，盤點就會把每個值當成各自要證明的範圍。展開等價類是測試的事。分辨方式：brief 時看依據那句話是在定義一條規則（列出的值只是例子），還是對不同值各有要求；final 校準時以程式碼是否走同一個判斷為準。

### 第四關：量級

`spec.md` 沒有編號的業務規則表可以當分母，所以先自己建一個：**在心裡（不寫進文件）列出本 feature 的業務規則清單**，以**約一條規則一條 VC** 為錨，再加上權限攔截與跨切片一致性各數條。一般功能 **6-10 條**。

**超過 12 條時，回頭重跑第一關，不要調降判準去遷就已經寫出來的條目。** 超量幾乎都是欄位級驗收混進來了，而它們每一條單看都合理——這就是為什麼要靠計數當觸發器，不能靠讀起來的感覺。

### 三條排除規則（寫入前逐條檢查，任一命中就不要放進來）

1. **`spec.md` 任何章節已經寫明的，不重複**——不限於驗收段落，Testing Decisions 與技術澄清也算。
2. **只是重述本文件其他章節的，刪**——「舊頁面已移除」屬於「目標與範圍」；「本次無 schema 變更」屬於 final 的「文件資訊」。
3. **能被單一票完整擁有的，留在票裡**——這是第一關的另一種問法，寫完整張表後再掃一次，通常還會再掉幾條。

### 欄位

| 欄位 | 內容 |
| --- | --- |
| `VC-xx` | 編號。**跨文件的追溯鍵，一旦給出就不重編、不合併、不拆條** |
| 條件 | 一句話：明確前提 + 可觀察結果。需要三行才講得清楚，代表在重述需求或條件複合 |
| 依據 | brief 指回 `spec.md` 的 user story／業務規則，或本文件的決策；final 改指本文件的 `BR-xx` 或設計章節（見 final 第 4 步）。**指不回去的是新需求**，停下來請使用者先改 `spec.md`。第二關的強度校準吃這一欄 |
| 驗證方式 | 自動化測試／手動操作／查資料庫／讀程式碼，擇一。`to-acceptance-map` 的判定會吃這一欄 |

`驗證方式` 有護欄，因為 `to-acceptance-map` **不得推翻本欄**——填錯會讓真正的缺口被藏進「不適用測試」而沒有任何人發現：

- **使用者觀察得到的行為一律填 `自動化測試`。** 錯誤訊息、資料出不出現在結果中、排序、分頁、預設值都測得到。**判斷不了就填 `自動化測試`**，讓盤點時把它報成需補測試，由使用者裁決。
- 只有純視覺版面、需要真實外部環境而專案沒有建置那層測試、或約束的是實作路徑而非行為，才填其他三種，且要能一句話說出為什麼測不到。這三種**合計五條以內**；明顯更多時，多半是第一關沒跑乾淨。

## 修訂模式

開發中途改動時使用，通常由 `to-change-request` 委派，也可直接調用。

- **就地改**受影響的章節與 `VC-xx`：新增給新編號，改寫就地改，取消的**保留該列並標記「已取消（YYYY-MM-DD，原因）」**——編號不回收，否則追溯鍵會對不上先前貼出去的內容。
- 在文件末尾的「修訂紀錄」追加一列：日期、改了什麼、連帶改了 `spec.md` 的哪一段（若有）。文件已是 `final` 時（例如補「已知限制」），追加到「附錄：修訂紀錄」，不寫 `spec.md` 的段落，修改內容也依 final 的自足規則寫。
- **判斷不需修改時，回報理由，不得只說「不需修改」。** 最常見的合理情況是改動只影響 final 才補的紀錄內容（資料模型、介面、實作落點），brief 的約束不受影響——這時要點名是哪一類內容、為什麼不在 brief。
- 需求層級的改動（要不要做、做到什麼程度）**不在本 skill 處理**，`spec.md` 的權威不容繞過——請使用者走 `to-change-request`。
- 已完成的 ticket 一律不回頭修改。被推翻的行為靠新票收掉，現行事實靠本文件的 `VC-xx` 記錄。
- **`to-acceptance-map` 之後決定不補的覆蓋缺口**，寫進「已知限制」：每項點名 `VC-xx`、缺的是什麼（沿用盤點寫出的反例）、為什麼接受。`to-acceptance-map` 重跑時讀這裡判為「已接受」——只寫在盤點檔裡的決策，下次覆寫就消失了。文件狀態維持 `final`，修訂紀錄照常追加一列。

## final 模式

整條 branch 的 ticket 全部完成後跑一次，**在 `to-acceptance-map` 之前**。六個步驟依序做完，**不要跳過第 2 步直接組版**。

final 的產出是主 Issue 的 SA/SD：**以 `to-engineering-spec` 的 `document-template.md` 為模板，由既成事實重新組裝，不是在 brief 上補章節。** brief 的骨架（目標與範圍、方案輪廓、關鍵決策）是給拆票用的，保留它就會讓交付物停在計畫的形狀；brief 的內容依第 4 步的對照表拆進模板的各章。

### 讀者與寫法

讀者是**審查這次變更的人**與**日後接手維護的工程師**，兩者都沒參與開發過程，手上只有這一份文件。目標是**思路清晰、明確、人讀得懂**：讀完知道改了什麼、規則是什麼、為什麼這樣做、上線要注意什麼、哪些地方沒有被保證。

- **每章先講結論，再講細節。** 讀者只讀每章第一段，也要知道這章的重點。
- **只寫本次改變的部分。** 沒變的既有行為一句帶過或不寫；不要為了完整把既有欄位順序、既有紀錄格式、沿用的設定重抄一遍。
- **程式識別名稱只出現在「模組責任」。** 其他章節用角色描述（「租戶管理專用的平板狀態寫入元件」），不用類別名、方法名、檔名。讀者不需要看過程式碼就能讀懂規則。
- **文件用詞與畫面文字不同時，第一次出現就對照。** 例如程式與規格寫「層級」、畫面顯示「組織」，寫成「層級（畫面顯示為組織）」，之後統一用一個詞。
- **同一件事只講一次。** 規則的理由寫在該 BR 的「理由」，不在設計決策、模組責任、資料存取再講一遍；其他地方要提，寫一句並指向該 BR。
- **沒有內容的格子、區塊、列不留。** 說明欄填「—」的列、只寫「見某章」的區塊、只有一個可能值的欄位，都刪掉。
- **不留開發流程的痕跡。** 開發中使用的工作流程用語與產物，其他人看不懂也用不到：`spec.md`、User Story、ADR、`CONTEXT.md`、brief、切片、seam、skill 名稱都不出現。需要的內容改寫成讀者看得懂的敘述攤回內文。票編號例外，因為票會貼在 Issue 留言。

### 1. 校準 `VC-xx`（先做這件事）

比對每條 `VC-xx` 與實際交付，逐條處理並在回報中明列：

- **仍成立** → 不動。
- **行為改了** → 就地改寫條文（編號不變）。
- **被後續決定取消** → 標記「已取消」，保留編號與原因。
- **實作做了、但當初漏收的跨切片要求** → 新增一條，給新編號。
- **行為沒變，但條文比實際交付寬、或條件複合** → 就地收斂成可終結的條文（編號不變）。brief 是在看不到實作的情況下寫的，寫寬是常態；**這一類在文件裡沒有任何症狀，只會在 `to-acceptance-map` 變成覆蓋不足**，所以要逐條主動跑「驗證條件」的第二關與第三關，不能只看行為有沒有改。

**主動找漏收的跨票一致性。** 票在手後，逐條業務規則問：**這條規則是不是由兩張以上的票各自實作一段？** 典型是「畫面上的候選或篩選」與「存檔時的檢查」分屬不同票、「列表」與「匯出」分屬不同票。是的話，兩端是否一致就是任何單張票都驗不到的要求；沒有對應的 `VC-xx` 時新增一條。這一類 brief 時看不到票，最容易漏。

**不因為切票後落在單一 ticket 就取消。** brief 寫下的條目是依性質收進來的業務規則效果；票在手後發現某條剛好只由一張票驗收，它仍然是這個 feature 必須成立的結果。拿掉它，`to-acceptance-map` 會少盤點一條規則，該條規則的測試也會對不上任何 `VC-xx`，被誤報成疑似失效或漏掉同層重複的檢查。各票開發當下的驗收是快照，後開的票可能已經改動它的行為，盤點正是在 branch 收尾時重新確認這件事。

判斷依據是程式碼與 ticket 的驗收核對表，不是記憶。**這一步是 final 的重點之一**：`to-acceptance-map` 的整份盤點都建立在這張表上。

### 2. 掃過全部資訊面向（一個都不能跳）

讀程式碼、ticket 核對表、`git diff` 與 `spec.md`，對 `to-engineering-spec` 的必查維度逐項做出結論。**這一步是分析，不是組版**——不要邊掃邊開 heading。

系統邊界 ／ 角色與權限 ／ 狀態與動作語意 ／ 使用者介面 ／ 業務規則 ／ 模組責任 ／ 對外契約 ／ persisted data 與 schema ／ 交易、併發與存取代價 ／ 相容性與 rollout ／ 未解問題 ／ 驗證條件 ／ 已知限制。

每項的結論依模板的「章節存在門檻」判定：**獨立成章** ／ **併入相鄰章節** ／ **一句話帶過** ／ **不適用，不寫**。門檻看的是**這個面向本次有沒有被動到、有沒有設計資訊**，不看整份文件大不大：一個只動到三個面向的案子，那三章照樣寫到定稿標準。

**一條 branch 做了數個互不相關的主題時**（例如同時做了資料清理、匯出格式與綁定規則），各章內依主題分組，業務規則依主題連續編號，不把不同主題的規則混在同一節。

### 3. 補查讀者最需要、但開發過程最容易漏寫的事

下面五項不會出現在任何一張票的驗收裡，開發時也沒有人會主動寫下來，卻是讀者最常回頭問的。**每一項都要實際查程式碼或資料流再下結論**，結論寫進回報；有內容才寫進文件。

| 要查的事 | 怎麼查 | 有內容時寫在 |
| --- | --- | --- |
| **既有資料在新規則下會怎樣** | 舊規則寫出來的資料（狀態、關聯、旗標），在新規則下會不會被當成例外、查不到、或被擋下；需不需要清理，還是接受 | 變更影響 |
| **上線時要特別處理的東西** | 部署產出物（前端打包檔、快取版本參數、設定檔）、一次性 SQL、必須先完成的前置作業與執行順序 | 變更影響 |
| **前置依賴** | 必須先合併或先上線的其他 issue、分支 | 文件資訊 |
| **範圍外仍走舊邏輯的路徑** | 本次規則約束的資料，還有哪些寫入路徑（其他頁面、API、批次、匯入）沒有跟著改；它們現在會怎麼寫 | 範圍與非範圍的「不包含」說明；會造成誤解或風險時寫進已知限制 |
| **沒有自動化驗證的行為** | 需求或票明定不寫測試、只在畫面人工確認過的行為 | 已知限制，寫明怎麼確認過 |

查不出結論的（例如需要查正式資料才知道筆數），寫進「待釐清事項」，不要略過。

### 4. 依模板組裝

章節順序、各章寫法、行數預算與「章節去留」一律照 `document-template.md`，寫作規則照 `writing-rules.md`。模板是為動工前的工作版寫的，final 是實作後的交付版，**差異只有下表**，其餘照模板：

| 模板的設計 | final 的做法 | 理由 |
| --- | --- | --- |
| 「文件資訊」 | 只留「所屬模組」、「前置依賴」（有才寫）與 Schema 是否變更；不寫 `Matt Spec`、`相關 ADR`、`文件狀態`、`專案類型`。ADR 裡與本次有關的決策與理由，攤回對應 BR 的「理由」。文件狀態維持標題下方 `文件狀態: final (YYYY-MM-DD)` 那一行 | `spec.md` 與 ADR 都不會貼上 GitLab；其餘欄位對讀者沒有資訊 |
| 「本次改動」表與「範圍與非範圍」 | **不寫「本次改動」表**，改由「範圍與非範圍」承接：「包含」每列用一句白話寫出這區改了什麼，並指向對應的 BR 或功能介面小節 | 兩張表列的是同一批區域，讀者要看兩遍 |
| 「範圍與非範圍」的「不包含」 | 只列**讀者可能誤以為包含**的項目，說明欄必須有內容；只有開發者在意的項目（測試常數、內部重構）不列 | 「不包含」的價值在擋掉誤解 |
| 「不重寫 user stories，需求細節見 spec.md」 | **需求內嵌**：業務規則的「規則／判定」與功能介面承接 `spec.md` 的需求內容，包含錯誤訊息原文、邊界值與預設值 | 讀者手上只有這一份 |
| 「狀態與流程」的流程圖 | **判定表已能表達時不畫圖**（條件不超過三個、沒有迴圈，通常就是）。真的要畫時只畫業務判斷，不畫本次沒動的既有檢查與併發控制的實作節點；檢查的先後順序重要時，在該 BR 的「判定」寫一句順序 | 把業務判斷與實作步驟混在同一張圖，線路交叉、讀者分不出哪些是規則 |
| BR 的 `> **設計決策**：` | **BR 內不寫**。被排除的方案與「不可偏離」的理由寫進該 BR 的「理由」；`設計決策` 標記只用在 BR 以外、沒有「理由」段可放的地方（功能介面、模組責任、資料存取與一致性），一章至多一個 | 交付時沒有「實作方向」可對照，BR 內的設計決策只會重述理由 |
| BR 的「實作約束」 | 只在有實質內容時寫（交易、順序、冪等的具體要求）；只是「見某章」的轉址不寫 | 轉址沒有資訊 |
| `> **實作方向**：`、實作示意 | 不用 | 交付時都已實作，「可調整」的約束程度沒有對象 |
| 「模組責任」 | 拿掉「約束程度」欄；只列新增的邊界、非直覺的落點、共用元件的擴充，一般分層不列 | final 的每一列都是既成事實，那欄只會有一個值 |
| 「資料存取與一致性」 | 只寫本次新增或改變的決策；沿用既有的設定（例如隔離等級）不寫 | 否定或沿用的句子對讀者沒有增量 |
| 「交給 to-tickets」章 | 不寫 | 給下游 agent 的機器契約，交付時沒有下游 |
| 驗證條件的「依據」欄 | 改指本文件的 `BR-xx` 或設計章節；**`VC-xx` 的編號與條文不因改依據而變動** | User Story 編號在 GitLab 上無從查起 |
| 定稿的「驗證結果」欄 | 不加 | 盤點結果由 `acceptance-map.md` 貼在 Issue 留言 |
| 「附錄：偏差與待處理」 | 第 5 步裁決後仍保留的偏離才寫 | 見第 5 步 |
| 「附錄：修訂紀錄」 | **brief 的修訂紀錄不帶進 final。** 開發中途的改動已經反映在各章的現況，過程留在 Issue 留言的票裡。final 之後再修訂（例如補已知限制）才開始記 | 讀者要的是最終狀態，不是開發過程 |
| —— | `## 已知限制`：第 3 步與 `to-acceptance-map` 之後接受的限制，放在「驗證條件」之後、附錄之前。對應覆蓋缺口的項目點名 `VC-xx` | `to-acceptance-map` 依章名讀它 |

brief 的內容拆進模板的對照：

| brief | final |
| --- | --- |
| 目標與範圍 | 背景與目的、範圍與非範圍 |
| 方案輪廓 | 依內容拆進業務規則（規則與判定）、功能介面、模組責任、資料存取與一致性 |
| 關鍵決策 | 對應業務規則的「理由」；影響多條規則的，寫在資料存取與一致性或模組責任 |
| 驗證條件 | 章名、編號、條文保留，依據改指 `BR-xx` |
| 風險與待釐清 | 仍未解決的進待釐清事項；已解決的依性質搬進對應章節 |
| 修訂紀錄 | 不帶進 final（見上表） |

**ticket 可以引用。** 拆票的 issue 會貼在主 Issue 的留言裡，讀者找得到；寫 ticket 編號（例如「由 05 交付」）不違反自足規則。但不要把逐票的 commit、測試條數或驗收明細摘進來——留言裡已經有了。

**模板的精簡規則照用，但它們管的是重複與越界，不是篇幅。** `writing-rules.md` 的去重、可推導、否定資訊預算都適用；不適用的是「為了讓文件變短而併章、縮成一句」——進得了門檻的章節照模板寫完。

### 5. 標出與 brief 的落差

`方案輪廓` 或 `關鍵決策` 與實際做法不同時，**列出來讓使用者裁決**是改文件，還是這確實是需要記錄的偏離。不得靜默對齊任一邊。使用者決定保留為偏離的，寫進「附錄：偏差與待處理」。

### 6. 送出前自檢

final 會被整份貼進 GitLab，作為主 Issue 的本文；拆票的 issue 與 `acceptance-map.md` 貼在它的留言。逐項確認：

**自足**
- 沒有 `spec.md` 的痕跡：連結、User Story 編號、「詳見需求文件」都沒有出現。
- 沒有開發流程用語：ADR、`CONTEXT.md`、brief、切片、seam、skill 名稱都沒有出現。
- 不留本地相對連結（`./spec.md`、`./issues/xx.md`）、`.scratch/` 路徑、`$to-tickets ...` 之類的指令行、skill 名稱、TODO 與內部工作註記。

**正確**
- `VC-xx` 逐條計數，與第 1 步校準後的結果相同；「驗證條件」與「已知限制」的章名沒有改寫。
- 錯誤訊息原文、邊界值、交易與併發約束：抽 3 條比對程式碼，與實際一致。
- 第 3 步的五項都有結論；查不出結論的在「待釐清事項」。

**好讀**
- 只讀每章第一段，就知道這章的重點。
- 「模組責任」以外沒有類別名、方法名、檔名。
- 文件用詞與畫面文字不同的地方都有對照。
- 沒有說明欄填「—」的列、只有轉址的區塊、只有一個值的欄位。
- 同一個理由沒有在兩處完整出現。
- 有流程圖時，說得出判定表為什麼表達不了。
- 每一章都過得了模板的章節存在門檻：沒過的不留空殼，過了的沒有被縮成一句。

「待釐清事項」若仍有未結項目，整章保留，並在回報時提醒使用者那些會被一起貼出去。不另外產生 `_deliverable.md` —— 本文件自己就是交付物。

### final 回報格式

回報訊息（不寫進文件）要包含：

1. `VC-xx` 校準結果：仍成立／改寫／收斂／取消／新增，逐條列；表末給出總條數，超過 12 條要說明為什麼留下。新增的跨票一致性條目寫出是哪兩張票的哪兩端。
2. 第 2 步的必查維度，各自的結論（獨立成章／併入／一句話／不寫），**包含判定為「不寫」的那些及理由**——這是使用者確認你沒漏查的唯一依據。
3. 第 3 步五項的查證結論，各自寫在文件哪裡或為什麼不寫。
4. 業務規則清單（`BR-xx` 與標題），以及各條 `VC-xx` 改指的依據。
5. 與 brief 的落差清單，請使用者裁決。
6. 第 6 步自檢的結果；仍有待釐清事項時點名。

## 適用門檻與退場

本 skill 的 final 與 `to-engineering-spec` 定稿同等完整，兩者差在**設計什麼時候定版**。以下**兩項以上**為真時，設計必須在動工前定版並經過審查，改用 `to-engineering-spec`：

1. 新增或調整角色與權限體系。
2. 涉及 schema 變更且牽動交易邊界或併發控制。
3. 需要改變既有架構假設，或跨三個以上模組的職責重劃。
4. 公司要求在動工前提交完整技術設計供審查。

反過來，改動小到「不動架構假設、不跨模組、無 schema 變更、VC 湊不滿 5 條」時，**直接告訴使用者本文件可以不寫**，走 `to-spec → to-tickets → implement` 即可，不要為了流程完整而生一份沒人讀的文件。

兩者之間還有第三種、也是最常見的情形：**文件要寫，但不需要展開全部章節。** 它不是另一種模式，不改文件狀態、不改檔名——由 final 依模板的章節存在門檻處理。

## 與其他 skill 的邊界

| 事實 | 權威 |
| --- | --- |
| 需求、範圍、行為 | 開發期間是 `spec.md`（Matt `to-spec`）；final 交付時內嵌進本文件，成為自足的快照 |
| 驗證基準 `VC-xx`、方案輪廓、關鍵決策 | **本文件** |
| SA/SD 的章節結構、章節存在門檻、寫作規則 | `to-engineering-spec` 的 `document-template.md` 與 `writing-rules.md` —— final 照用，本 skill 只列差異 |
| 難以回復、影響超出本 feature 的決策理由 | ADR（`.ai/docs/adr/`） |
| 工作切片、逐票 commit 與驗收明細 | `issues/` 下的 ticket —— 不是需求或驗證的權威，也不需要摘進本文件 |
| 測試對 `VC-xx` 的覆蓋情形 | `acceptance-map.md`（`to-acceptance-map`） |
| 專案術語 | `.ai/CONTEXT.md` |

- **`to-tickets`** 讀 `spec.md` 與本文件的 brief 拆票（`方案輪廓`、`關鍵決策` 是切分的輸入）；本 skill 不自己拆、不調用它、不改 `issues/`。拆票過程若發現 brief 的方案輪廓站不住，回本 skill 修訂模式，不要在票裡默默改設計。
- **`to-acceptance-map`** 讀本文件的 `VC-xx`；本 skill 不做覆蓋盤點，也不把測試結果寫進本文件。
